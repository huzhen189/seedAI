# AI 生成器平台 — AI 核心端细节（Agent 子系统）

> 本文档定义 **AI 核心（Agent 子系统）** 的实现细节：**模型抽象层、Router+Skill 编排、generate_site 内层多 agent、思考链路事件、Skill/Tool 注册表与本地落地、RAG、记忆闭环、COS 预览投递、优化方案、资源层连接池、四角色编排、后置 QC**。
> 跨服务架构见《项目总览》；前端契约见《前端细节》；业务接口见《业务端细节》。
> 全文以「当前方案」表述。代码已落地于 **`backend/app/agent/`**（与业务层同进程，见 §1），旧双服务时代的 `backend/ai_service/`（独立 `:7102` 进程、经 httpx 转发）已于 2026-07-26 废除，本文档不再保留其任何描述。

## 1. 技术栈与职责（同进程子系统）

- **进程归属**：AI 核心不是独立服务，而是**单进程 FastAPI 应用 `backend/app/` 的内嵌子系统**，随 `uvicorn app.main:app`（监听 `:7101`）一起启动。业务层（`backend/app/*.py`：projects / proxy / auth 等）与 Agent 子系统（`backend/app/agent/`）**共享同一个进程、同一份 Redis / MySQL 连接**。历史上「业务服务 `:7101` + AI 服务 `:7102` + httpx SSE 转发」的架构已废除，SSE 改为进程内 `proxy.py` 订阅/`重序列化` 队列事件（见《业务端细节》§5 / 《前端细节》§3）。
- **框架**：FastAPI + LangGraph + SQLAlchemy(async，经 `shared/db.py` 直连 MySQL)。
- **职责**：模型抽象层（Provider 注册表 + FallbackRouter）、Router+Skill 路由、generate_site 内层 LangGraph 轻量多 Agent、RAG（Chroma 远程 HTTP）、流式生成与思考事件产出、四角色编排（RoleOrchestrator）、后置 QC。
- **数据归属（同一进程，无跨服务边界）**：
  - MySQL：经 `shared/db.py` 直连（用户 `account`、项目 `Project`、会话 `Conversation`、追踪 `Trace`、反馈 `Feedback`、意图槽位 `IntentSlots`、断点续跑 `UserState` 等持久化表）——**Agent 子系统直接读写，不再经业务服务转发**。
  - Chroma：远程 HTTP（`CHROMA_URL`，v2 API）单例客户端直连，承载 9 个向量集合（§9）。
  - Redis：与业务层共用同一实例，承载 `gen:stream:<tid>` 进度流 / `queue:generate` 任务队列 / `cancel:<tid>` / `clients:<tid>` / `an:*` / `ai:*` 统计（§15）。

## 2. 模型抽象层（Provider / FallbackRouter）

目标：新增一个模型 = 写一个适配器 + 注册，前端与业务层无感。实现位于 `backend/app/agent/providers.py`。

```python
from abc import ABC, abstractmethod
from typing import AsyncGenerator

class BaseLLMProvider(ABC):
    id: str
    label: str
    @abstractmethod
    def chat_stream(self, messages: list[dict], **kwargs) -> AsyncGenerator[str, None]: ...

PROVIDERS: dict[str, BaseLLMProvider] = {
    "deepseek": DeepSeekProvider(api_key=settings.DEEPSEEK_KEY),
    "qwen":     QwenProvider(api_key=settings.QWEN_KEY),
    "hy3":      HY3Provider(api_key=settings.HY3_KEY),
}
```

- **HY3**：OpenAI 兼容，`base_url=https://tokenhub.tencentmaas.com/v1`，model=`hy3`。
  - **关键坑（2026-07-18 修复）**：`HY3_API_KEY` 必须是腾讯 TokenHub 控制台（https://console.cloud.tencent.com/tokenhub/apikey）创建的**真正 API Key（形如 `sk-...` 或令牌串）**；文档早前记的 `TokenHub_QCSLinkedRoleInInitialization` 只是「关联角色名」，不是可用 Key，直连会被 `401002 API Key 不存在/签名校验失败` 拒绝。Demo 测试可用 `HY3_API_KEY_DEMO`（示例临时 key）。
- **Qwen（默认模型，2026-07-27 切到 token-plan）**：OpenAI 兼容，`base_url = https://token-plan.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`（阿里云 MaaS 私有工作区 token-plan）。统一由 `settings.qwen_base_url` 提供——chat（`providers.py`）、embeddings（`chroma.py` + `rag_retrieve.py`）全部共用同一字段；**`.env` 的 `QWEN_BASE_URL` 覆盖优先级最高**。`QWEN_EMBEDDING_KEY` 须为 token-plan 工作区下签发的 key（形如 `sk-ws-...`），否则与地址不匹配导致 embeddings 调用失败。废弃的 `QWEN_API_HOST` / `QWEN_DASHSCOPE_URL` / `qwen_api_host` 已清理。
- **扩展**：新增模型只需实现 `BaseLLMProvider` 并注册一行。
- **配置加载（2026-07-18 修正）**：`config.py`（`app/config.py` 为 `shared/config.py` 的 re-export shim）用 `Path(__file__).resolve().parents[3] / ".env"` **绝对路径**加载项目根 `.env`，不受启动目录影响。
- **FallbackRouter**：在 `PROVIDERS` 之上加降级路由。
  - 主模型由用户 **套餐/层级(plan/tier)** 决定（免费用便宜模型如千问，付费可用贵的如 DeepSeek/HY3）。
  - 用户前端可**手动勾选模型优先级（主 + 备）**，后端按指定顺序回退。
  - 主模型 429/超时/5xx 时按序回退；发生回退时思考事件带 `degraded: true`，前端显示「已降级」。
  - **默认降级序：HY3 → Qwen → DeepSeek**（用户指定可覆盖）。
- **端点（调试用，同进程内）**：`GET /models` 返回 `[{id, label}]` 供前端选择器；`GET /skills` / `GET /tools` / `GET /registry` 查看已注册能力（admin 看板可对接）。生成入口为业务层 `POST /api/chat`（SSE），不再是独立的 `/generate`。

## 3. 编排架构（Router + Skill + Hybrid）

- **外层 Router（混合级联意图识别 + Skill 分发，v1.2.2 起唯一分类器）**：`router.detect_intent_v2()` 仅调用 **单一分类器** `cascade.classify_v3()`，内部执行四级混合级联（SIR 双轨已于 v1.2.2 彻底删除）：
  1. **规则强信号直路由**：`rulesmatcher.match_rules()` 命中强信号即进入候选（零 LLM 成本）。
  2. **向量召回 top5**：`vector_store.retrieve_intents()` 语义召回候选意图。
  3. **大模型有界终判**：`classify_v3` 在召回候选内做有界终判，输出 `{level1, level2, confidence, industry}`。
  4. **置信门控**：高→直接执行（`route`）；低→澄清（`clarify`，下发结构化选项卡 + 自由输入，前端底部浮动面板暂停流程等待用户确认回填，再由 `clarified=1` 续跑补齐槽位，**非 2 轮对话**）；新奇度兜底（top5 全 < `intent_novelty` → 闲聊）。
  - **CLARIFY 事件（v1.2.11 增强）**：Worker 下发 `clarify` 事件时携带结构化选项——`options:[{label, recommended}]`、`multi`(是否多选)、`free_text_hint`(自由输入提示)；前端以**底部浮动面板**渲染（详见《前端细节》§3 / §14）。用户确认后带 `clarified=1` 重发，答案作为 `q` 追加到对话历史，由 `pending_clarify` 重建意图直接路由执行。
  - **level1**（6 类）：`learn` / `code` / `build` / `doc` / `translate` / `unsupported`。
  - **level2**（17 子类）：在 level1 下细分（如 `learn/explain`、`code/fix`、`build/game`），完整矩阵见 docs/06。
  - **industry**（12 行业）：`restaurant`/`ecommerce`/`gov`/`edu`/`health`/`finance`/`game`/`personal`/`corp`/`tech`/`media`/`other`，仅 build/doc 时启用，注入 Planner 设计约束。
  - **阈值集中 `config.py`**：`intent_super_fast=0.90` / `intent_novelty=0.45` / `intent_commit=0.80` / `intent_clarify_lo=0.45` / `intent_clarify_max_rounds=2`；信号单一来源 `intent/signals.py` + `rules_catalog.json`。
  - Router 按二维映射 `(level1, level2) → skill_name` 分发到对应 Skill handler；handler 内部根据 `level2` 切换 System Prompt 模式。
- **内层仅对 `generate_site` 保留轻量多 Agent**：`Planner → Coder → Reviewer`，Planner 接收 industry 设计约束注入，Coder 根据 `level2=game` 切换 Three.js 游戏模式。
- **其余 Skill 单次 LLM 直出**：`write_code` / `generate_doc` / `explain` / `rag_retrieve` 无需多 agent 协作。
- **🆕 多意图拆分（v1.2.5 重构为 A+B 路由）**：用户单条超长提问若含多个独立意图，由 `intent/multi_intent.py` 的 `recognize_intents()` 拆为多个 `SubTask`，经 **DAG 编排器**（`core/orchestrator.py`）按依赖关系分层——同层 `asyncio.gather` 并行、跨层串行；各子任务独立 `run_skill` 产出，最终由**合并器**汇成一条连贯回复（`merge` 事件 + `__merge__` token）；**风险分级门控**：HIGH=拒绝、MEDIUM=确认后执行、LOW=自动执行（见 `run_safety`）。前端渲染见《前端细节》§14。
  - **A+B 路由（默认方案B 混合分层，必要时升级方案A）**：
    - **轻量门控**：仅当用户文本命中 ≥2 个意图大类（`_lightweight_multi_check`，零 LLM 成本）才进入拆分，否则整条当单意图处理，**零额外开销**。
    - **方案B（混合分层，默认快路径）**：确定性切段（`_segment_text`）→ 逐段复用单意图分类器 `cascade._classify_segment` → 合并相邻同意图续写段 → 连词/指代推断串行(依赖)/并行(独立)。
    - **方案A（LLM 深拆，升级兜底）**：方案B 未识别 ≥2 个有效子任务或平均置信 < `split_escalate_low_conf`(0.6) 时，升级 `split_by_llm`（单次 LLM 全局推理 + JSON 自愈修复环）。
    - **两路皆失败 → `is_multi=False`**，上层 `classify_v3` 当单意图处理，不阻断主链路。

**同进程调用关系**

```
前端 EventSource /api/chat (SSE)
   └─ backend/app 单进程
        ├─ [WebLLM 旁路] 前端本地首过(同构事件,失败回退)
        └─ proxy.py 接收 → 业务鉴权 / 配额 → agent 子系统
              ├─ Router(cascade.classify_v3): 规则强信号 → 向量召回 top5 → LLM 有界终判 → 置信门控
              ├─ Skill 分发(roles/RoleOrchestrator 可选增强)
              │    ├─ generate_site → {Planner→Coder→Reviewer}(LangGraph)
              │    ├─ write_code / generate_doc / explain / agent_chat → 单次 LLM
              │    ├─ rag_retrieve → Chroma(语义缓存)
              │    └─ 工具调用(browser_screenshot / cos_upload / fetch_url / web_search / image_generate / html_validate / file_io)
              ├─ 模型抽象层 + FallbackRouter → DeepSeek / Qwen / HY3
              └─ 产出经 gen:stream:<tid> 队列 → proxy.py _sse_lines() 重序列化转发前端
```

## 4. generate_site 内层（LangGraph + Plan-and-Execute + Reflexion）

内层状态图（LangGraph）：

```python
from langgraph.graph import StateGraph, END

class SiteState(TypedDict):
    spec: str          # Planner 产出(与 Coder 共享,不重复喂原始对话)
    html: str
    reviews: int
    passed: bool

def planner(state): ...      # 需求拆解 → spec
def coder(state): ...        # spec + style 约束 → html
def reviewer(state): ...     # 静态分析 + LLM 自审 → passed / 修改建议

graph = StateGraph(SiteState)
graph.add_node("planner", planner)
graph.add_node("coder", coder)
graph.add_node("reviewer", reviewer)
graph.add_edge("planner", "coder")
graph.add_edge("coder", "reviewer")
graph.add_conditional_edges("reviewer", route_after_review,
    {"pass": END, "retry": "coder"})   # ≤3 轮,避免死循环
app = graph.compile()
```

- **演进姿态（Plan-and-Execute + Reflexion）**：
  1. Planner 产出结构化页面规格（板块 / 布局 / 风格 / 技术选型）→ 作为 `plan` 事件推前端思考面板；
  2. Coder 严格按 `plan` 生成单文件 HTML（共享 plan 上下文）；
  3. Reviewer 按计划逐条核对 + 静态分析（§12 的 3-C）；不达标进入 **Reflexion 循环**：失败原因写入短期记忆 → 反思 → 重写（≤3 次）。
- 其余 Skill 是普通函数，单次 `PROVIDERS[model_id]` 调用即返回（无状态图）。
- RAG（§9）在 `generate_site` / `generate_doc` 的 Planner/Coder 前注入组件与记忆上下文（Chroma）。
- 各调用统一走 §2 模型抽象层 + FallbackRouter。

## 6. SkillRegistry（技能注册表）

核心是一个注册表 `SkillRegistry: dict[name → SkillEntry]`（`registry/skill_registry.py`）：

- `name`：技能名（如 `generate_site`）
- `intent_tags`：意图标签（辅助 Router 匹配，如 `["site","网页","页面"]`）
- `handler`：处理函数，或已编译的 LangGraph app
- `is_graph`：是否多 agent 状态图（`True` 时 `handler` 为 `graph.compile()`）
- `description`：给 Router / 前端展示的说明

**Router 分发流程**（v1.2.2 起统一走混合级联）：
1. `router.detect_intent_v2(messages, model_id)` 调单一分类器 `cascade.classify_v3()`，产出 `{level1, level2, confidence, industry}`（统一 `PipelineResult` 契约）；
2. `skill_for(level1, level2)`（委托 `catalog.skill_for`，单一来源 = `intent_catalog.json`，已移除硬编码 `INTENT_SKILL_MAP`）查得 `skill_name`；
3. `runner.run_skill(skill_name, ..., intent_info={level1, level2, ...})` 调 handler，handler 内按 `level2` 切 System Prompt 模式，`industry` 注入 Planner。

**引入新意图子类**：在 `intent_catalog.json` 加意图条目（`skill` 字段即映射来源）→ Router 自动识别，**无需改 handler**（handler 收不认识的 `level2` 时用默认 prompt）。

**动态发现**：`registry/__init__.py` 的 `bootstrap()` 导入 `skills/` + `tools/` 包完成注册，并扫描目录支持自定义 Skill/Tool 热插拔。

## 7. ToolRegistry（工具注册表）

**Skill vs Tool 区别**：
- **Skill**：对外暴露的「一个完整任务能力」，由 Router 按意图分发（如 `generate_site` / `explain`）；一次调用产出完整结果。
- **Tool**：Skill 内部 agent 可调用的「原子操作」，经 LLM **function calling** 暴露给模型，模型自主决定何时调用（如向量检索、COS 上传、代码执行、HTTP 请求）。

核心注册表 `ToolRegistry: dict[name → ToolEntry]`（`registry/tool_registry.py`），字段：`name` / `schema`(JSON Schema) / `func` / `scope`(`internal`|`user_exposed`) / `risk`(`safe`|`dangerous`)。

**Tool 来源分类**：
- **A. 内置工具**：代码内用 `@tool` 装饰器实现并注册（如 `rag_retrieve` / `cos_upload` / `web_search` / `code_run`）。
- **B. 运营 / 用户贡献工具**：一个 Python 文件 + schema 声明，放入 `tools/` 目录；启动扫描自动注册。
- **C. 第三方 MCP 工具（规划中）**：接外部 MCP server，协议自动将 MCP 能力转为 tool schema（如高德地图、GitHub）。

**`rag_retrieve` 双入口**：对外是 Skill（用户说「检索我的组件库」→ Router 分发返回上下文）；对内是 Tool（`generate_site` 内部 Planner 检索上下文时调用增强质量）。

**引入新内置 Tool**：写函数 + `@tool(name=, schema=, scope=, risk=)` → `register_tool(...)` → Skill 内部 agent 经 function calling 即可见，Router / 核心无需改动。

## 9. RAG 设计（Chroma，9 集合）

Chroma 为远程 HTTP（`CHROMA_URL` v2 API），经 `knowledge/chroma.py` 单例 `HttpClient` 直连。**集合结构在进程启动时由 `ensure_collections()` 确定性重建**（重置数据后删除空集合，重启即恢复结构）。全部 9 个集合（单一事实来源 `_ALL_COLLECTIONS`）：

| Collection | 内容 | 何时写入 | 何时检索 |
|-----------|------|---------|---------|
| `components` | 优质组件 / 页面模板片段 + 描述 | 运营预置 / 沉淀 | 生成前：检索 Top-K 拼进 Prompt，提升质量 |
| `memory` | 用户历史项目摘要 / 对话要点 | 每次生成后异步写入 | 生成前：检索该用户相关历史，注入上下文 |
| `cache_gen` | 相似 prompt → 历史产物（5-C） | 生成后回写 | 生成前查（命中复用），省 token |
| `user_preferences` | 用户偏好（蒸馏沉淀） | 蒸馏写 | 生成前检索注入 |
| `project_memory` | 项目级记忆 | 蒸馏写 | 生成前检索注入 |
| `project_code` | 项目代码片段索引 | P4 代码索引写 | 检索复用 |
| `error_patterns` | HTML/CSS 常见错误种子（20 条） | 预置 | 修复闭环检索 |
| `intents` | 意图类别 / 规则 | 预置 | 意图向量召回 |
| `conversation_context` | 对话上下文向量（边界检测） | 实时写 | 上下文连贯检索（相似度阈值 0.40） |

**流程**：用户需求 → Embedding → Chroma 检索（components + memory + cache_gen + 项目/用户记忆）→ 拼装增强 Prompt → 调模型 → 生成 → 异步回写 memory / cache_gen。

- **Embedding**：`_ef()` 优先级——① 配 `qwen_embedding_key` 时用 **Qwen `text-embedding-v3`**，`api_base` 取 `settings.qwen_embedding_base_url`（私有 MaaS 工作区）；② 否则本地 `SentenceTransformer(all-MiniLM-L6-v2)` 兜底（无需 API key）。已移除 DeepSeek embedding 分支（DeepSeek 无 embedding 端点）。
- **注入上限**：`_RAG_INJECT_MAX_CHARS = 6000`，防止 prompt 过长。
- **重置约定**：`scripts/reset_all.py` 重置时只清 `memory/cache_gen/user_preferences/project_memory/project_code`（保留 `components/error_patterns/intents/conversation_context` 预置/结构）。

## 10. 记忆系统闭环

本系统的「记忆」不只有 Chroma，而是一个**多层读写闭环**（同进程直接读写 MySQL + Chroma + Redis）。

**记忆分层**：

| 层 | 载体 | 内容 | 生命周期 | 读写时机 |
|----|------|------|---------|---------|
| 短期记忆 | MySQL `Trace` / `TraceEvent` | 本次会话完整事件流 | 一次提问；结束落库可回放 | 实时写；不进向量库 |
| 长期记忆（用户） | Chroma `memory` | 用户历史项目摘要 / 对话要点 | 跨会话、跨项目 | 生成后异步回写；生成前检索 |
| 组件记忆 | Chroma `components` | 优质组件 / 模板库 | 长期（运营沉淀） | 运营预置；生成前检索注入 |
| 语义缓存 | Chroma `cache_gen` | 相似 prompt → 历史产物（5-C） | 长期 | 生成前查（命中复用）；生成后写 |
| 意图槽位（DST） | Redis(热) + MySQL `intent_slots`(冷) | 多轮对话槽位 | 会话级（TTL 滑动） | 逐轮 save/load（§11） |
| 断点续跑 | MySQL `user_states` + Redis TTL 3h | v4 续跑状态 | 会话级 | 暂停/恢复（见《业务端细节》§9） |
| 反馈记忆 | MySQL `Feedback` | 1–10 评分 + 评论 | 长期 | 用户评分后写；既统计又回归 |

**检索闭环流程**：
```
[0] 用户需求(prompt)
 [1] 构造查询: A 原始 prompt(稠密 embedding) + B Planner 结构化 spec 关键词 + C 意图 + D 项目上下文(account/user_id)
 [2] Qwen text-embedding
 [3] Chroma 检索 Top-K(混合召回): components + memory + cache_gen + user_preferences + project_memory
 [4] 拼装增强 Prompt
 [5] Router 分发 Skill        (cache_gen 命中 ⇒ 直接复用产物,省 token)
 [6] generate_site 内层(Planner→Coder→Reviewer)
 [7] 生成产物 HTML ──→ COS 投递(preview_url)
 [8] 异步回写 memory   [9] 异步回写 cache_gen   [10] 用户评分(1–10) → Feedback(统计+回归)
 [11] 优质产物(Reviewer 通过 + 高评分)经运营审核 → 沉淀 components
 ⇒ 闭环:读前增强 → 写后沉淀 → 模型越用越准、越省 token(自我改进飞轮)
```

**关键词来源（混合检索）**：稠密向量负责语义召回，关键词与 metadata 负责精确过滤 + 排序加权（A 原始 prompt / B Planner spec / C 意图 scope / D 项目用户过滤）。

## 11. 意图槽位（DST，#511）

多轮对话的槽位状态由 `intent/store.py` 管理，采用 **Redis(热) + MySQL(冷) 双层**（#511 可靠性设计）：

- **Redis（热，零延迟）**：以 `conversation_id` 为键缓存当前槽位 JSON。
- **MySQL（冷，持久兜底）**：独立 `intent_slots` 表（`shared/models.py:IntentSlots`），按 `user_id + project_id + conversation_id` 联合唯一约束（`uq_intent_slots_ucp`）upsert 一行；Redis miss 时回源 MySQL 并回填。
- 调用点在 `intent/cascade.py`：分类/澄清/续跑多处 `asyncio.to_thread(save_slots, ...)` 持久化；`load_slots` 优先 Redis、回退 MySQL。失败均静默，不阻断主链路。

## 12. 优化方案（1-C / 2-C / 3-C / 4-C / 5-C）

### 12.1 生成任务并发 → 1-C：队列 + Worker
- 生成请求经 **`queue:generate` 队列 + Worker（同一进程内的 asyncio 任务）** 消费，产出进度事件写入 **`gen:stream:<tid>`**（`redis.asyncio` Stream，可回放、`XREAD` with `after` 断点续传）。业务层 `proxy.py` 的 `_sse_lines()` 订阅该流并重序列化推前端 → `done` 结束。并发上限 = Worker 数（可配置）。
- 孤儿对账：`proxy.py` `run_orphan_reconciler(interval=30.0)` 周期 30s 扫描 `gen:stream` 中失联任务并兜底落库（`reconcile_orphaned_runs`），启动期 `reconcile_orphaned_runs()` 先行一次（见《业务端细节》§17）。

### 12.2 模型故障转移 → 2-C：跨模型降级路由
- `FallbackRouter` 按用户优先级 + plan 默认回退（§2）；`degraded: true` 标记透出前端「已降级」。默认序 HY3 → Qwen → DeepSeek。

### 12.3 产物可运行校验 → 3-C：静态分析 + LLM 自审
- Reviewer 两步：① 静态分析（`html_validate.py`：HTML 解析，检查 doctype、标签闭合、script 语法粗筛、禁止危险 API 如 `eval` / 注入外部源的 `innerHTML`）；② LLM 多轮自审（Reviewer 建议 → Coder 修订 → 再评审，≤3 轮）。不引入 Playwright 重依赖，显著降白屏率。

### 12.4 预览安全隔离 → 4-C：独立沙箱域 + 严格 CSP
- 独立子域（COS 默认域天然不同源）+ `sandbox="allow-scripts"`（不含 `allow-same-origin`）+ 严格 CSP（待绑定自定义域 + CDN 时回源重写 `default-src 'none'` + 白名单 CDN / 字体）。

### 12.5 生成结果缓存 → 5-C：语义相似缓存
- Qwen text-embedding 对用户 prompt 向量化 → 查 Chroma `cache_gen` → 相似度 > 阈值直接复用 / 微调上次 HTML，省 token。用户可「强制重生成」覆盖。依赖 §9 向量库。

## 13. 资源层连接池（Chroma / Redis，同进程）

- **Redis（redis.asyncio 连接池）**：`pool = redis.asyncio.ConnectionPool.from_url(REDIS_URL, max_connections=50, decode_responses=True, health_check_interval=30)`；客户端全局复用。`queue.py` 的 `RedisBackend` 强制 `protocol=2` 避开部分云 Redis 不支持的 `HELLO`(RESP3) 握手；构造时做一次真实 PING 探测，连不上即回退 `MemoryBackend`（进程内 asyncio 队列，开发足够）。`DEV_MEMORY_QUEUE=1` 或 `REDIS_URL=memory://` 可强制内存模式。
- **Chroma（单例 HttpClient + httpx 连接池）**：复用**单例 `HttpClient`**，注入自定义 `httpx.AsyncClient(limits=httpx.Limits(max_connections=50, max_keepalive_connections=20))` 复用 TCP 连接。启动时 `client.get_or_create_collection(...)` 确保集合存在。
- **MySQL（SQLAlchemy async 连接池）**：经 `shared/db.py`，`pool_pre_ping=True` + `pool_recycle=1800` 应对本地→云 NAT 空闲掐断（见《业务端细节》§13）。有 `MYSQL_URL` 即云库，不回退 SQLite。
- **统一约束**：客户端均在进程启动时初始化为模块级单例，关闭时释放；禁止请求内反复新建连接。

## 17. 四角色编排（v2.2.0，方案 B-轻）

- **稳健开关**：`ROLE_ORCHESTRATOR_ENABLED`（`handoff.py`，默认 `"1"` 开启）。设为 `0` 时 `queue.py` 回退使用原生 `Orchestrator`，本类不被实例化（便于快速回退排障）。
- **统计**：`ai:role:*` 在 `runner.run_skill` 单一路径记录（角色级分发/状态/耗时），与 `an:subtask`（技能级）互补，避免双记。

## 18. 上下文关联（v0.7.0+，沿用）

三层上下文的发送格式：`context_hint`(前端 WebLLM 检测) > Chroma 向量检索(后端降级) > 无。

- 前端 WebLLM `contextCheck()`：将当前消息 + 最近 12 条对话发给本地 Llama-3.2-1B，返回一句话上下文摘要。
- 后端 Chroma `find_relevant_messages()`（`conversation_context` 集合）：向量相似度 > 0.40（实测阈值，原 0.55 过于严苛）的保留。
- 意图分类器接收 `context_hint` 参数拼入 prompt。

> 取代旧版「三裁判并行」。详细实现见 `qc.py` + `scoring.py`。

### 20.1 模块 `qc.py`（v2.3.0 改造）
- **单裁判降本**：直接用「本次生成所用模型」跑一次 QC（单裁判），不再 deepseek/qwen/hy3 并行。维度仍 7 维（`scoring.SCORING_DIMENSIONS` 单一来源）：`correctness / completeness / readability / compliance / efficiency / craft / safety`，各 1-10 整数。
- **混合判定（降本）**：`compliance / efficiency / safety` 叠加 `run_safety` 确定性地板（零成本）；`correctness / completeness / readability / craft` 走 LLM 单裁判打分（`LLM_SCORING_DIMS`）。
- **复核判定**：`overall` 低于 `qc_solo_needs_review_overall`(默认 7.0) 即标 `needs_review` → 触发质量闭环重做（建站）或闲聊 Phase D 重答。低分打回由主链路闭环兜底，故不再需要多裁判互验。
- **韧性**：单次调用失败返回 `partial=True` 降级（不影响主链路落库 / 展示）。
- **输出结构（兼容旧三裁判版，可直接作为 SSE `qc` 事件 data）**：`{judges:[{model, valid, comment}], dimensions:{<dim>:{mean,variance,scores:[d]}}, overall, needs_review, safety_risk, partial}`（`judges`/`scores` 长度=1）。

### 20.2 注入点（`core/queue.py` 正常单 skill 路径）
- 累积 `token` 事件为 `assistant_text`；**拦截 `done`** 暂不发。
- 若 Reviewer 标记 `needs_review`（或强制 QC 路径），调 `run_safety(messages, project_constraints).risk_level` 得 `safety_risk`，再 `asyncio.wait_for(run_qc(...), qc_timeout_seconds)` → 先 `publish qc` 再 `publish done`。
- **质量闭环（v1.2.4，仍生效）**：当 QC 仍 `needs_review` 时，自动触发 `agent_review` 出 `fixed_code` → 重写磁盘 + 重传 COS（同 version 键）→ 重跑 `run_qc`；循环上限 `qc_fix_max_rounds`(默认 2)，收敛或达上限即停，`qc` 事件回带 `fix_applied`/`fix_rounds`。`qc_fix_enabled` 可关闭。
- QC 失败仅告警、绝不阻塞 `done`；`block/unsupported/confirm/options/error` 路径不跑 QC；编排(orchestrator)路径不接闭环（多文件站点风险）。

### 20.3 事件协议
- SSE 事件 `qc`（`TERMINAL_EVENTS` 不含它）；前端 `chat.ts` 监听 `qc` → `onQc`；气泡展示 QC 徽标，管理后台聚合绘图。

## 21. AI 核心编排统计（analytics.py）

> 与《业务端细节》§18 的 STAT 协同：Agent 子系统与业务层**同进程同 Redis**，统计统一写入，无需跨服务读写。

### 21.1 写入（queue.py 正常多意图路径）
- `core/queue.py` 在 split 分支：`t0_split=time.time()`，建 `sub_start`(各子任务开始时刻) 与 `sub_meta`(id→(skill,risk)) 映射。
- 监听编排事件：`subtask_start`→记开始时刻；`subtask_done`→算耗时 `record_sub_task(skill,'done',risk,dur_ms)`；`subtask_fail`→按 reason 映射 status(blocked/skipped/failed) 后 `record_sub_task(...)`；`merge`→缓存合并数据。
- 循环结束后：`rate=sc/(sc+fc)`、`dur_ms`，调 `record_orchestration(len(sub_tasks), 'mixed' if has_dep else 'parallel', dur_ms, rate)`。

### 21.2 聚合（analytics.py）
- `record_orchestration(...)`：`an:orch:total` + `:strategy:{s}` 计数 + `split_count`/`success_rate`/`duration_ms` 写 zset。
- `record_sub_task(skill, status, risk_level, duration_ms)`：`an:subtask:*` 计数。
- `record_generate_request()`：`an:generate:total` +1。
- `record_role(...)`：`ai:role:*` 角色级统计（§17）。
- `orchestration_stats()`：读上述键聚合出 总次数 / 策略分布 / 子任务数·成功率·耗时百分位数 / 子任务 status_dist·risk_dist·per_skill·耗时 p50-p99。
- 惰性连接：模块级 `_redis_client` 经 `aioredis.from_url(settings.redis_url, ...)` 缓存；连接失败降级为 `False` 静默跳过，不影响主生成链路。
- 质量维度 `record_qc` / `record_intent` / `record_rev` / `record_safe` / `record_llm_call` 分别写 `ai:qc:*` / `ai:intent:*` / `ai:rev:*` / `ai:safe:*` / `ai:llm:*`。
