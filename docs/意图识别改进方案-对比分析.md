# 意图识别改进方案 · 对比分析

> 背景：v1.0.8 已修复「建站需求不被读取」(RC1–RC4)，但分类层本身仍有误判——例如「做个网站难吗」会被 `rules.py` 的 `build_kw` 命中「做/网站」直接判为 `build`，而「我想做个网站」与「帮我用 React 做企业官网 3 页面」在分类器眼里几乎没有区分度。
>
> 本文把你的「五维信号模型」方案系统化，并与现状及另外 3 个候选方案做横向对比，给出分阶段落地建议。
>
> **补充（v2）**：在五维模型基础上，追加 4 项设计——① 模糊意图澄清机制（最多 2 轮主动反问）；② 可观测性（每次识别必记 JSON）；③ 规则热更新（免重启）；④ 整体三层管道架构（上下文重建 → LLM NLU → 规则校验决策）。见 §8–§11。

## 1. 现状盘点（v1.0.8 意图管线）

### 1.1 架构

```
classify_v2(messages)
   ├─ [0] 选项选择短路 (selection.py)  ← 用户回复待选项/指定 skill
   ├─ 发射 run_semantic (LLM 异步, ~2s)
   ├─ 并行跑 4 同步模块:
   │    ├─ run_rules      (关键词, 零延迟)   → build/chat + industry
   │    ├─ run_context    (历史话题, 零延迟) → correction (曾引发 RC2)
   │    ├─ run_safety     (安全, 零延迟)     → block/confirm
   │    └─ (汇总准备)
   ├─ _aggregate:
   │    权重 语义 70% + 规则 20% + 上下文修正 10%
   │    → 工具选择 (run_tools) → 决策路由
   └─ maybe_split (多意图拆分, 命中才调 LLM)
```

> 现状是「规则/语义/上下文/安全 并行 + 聚合」的扁平结构。下文 **§8** 给出目标态——**三层管道**（上下文重建 → LLM NLU 候选 → 规则校验决策），它即方案 C 的具象化，也是后续 P0–P6 的组织框架。

### 1.2 现状对各信号的覆盖度

| 你的信号 | 现状是否已覆盖 | 覆盖形式 / 缺口 |
|---|---|---|
| **信号1 语义显式度** | ✅ 部分 | `rules.py` 仅做「build_kw 任一命中→build」的**二元**判定，无密度分级（≥2 强 / =1 中 / 0 弱）。 |
| **信号2 需求完整度** | ❌ 缺口 | 完全没有「约束计数」。「做个网站」(0 约束) 与「React+3 页面+表单」(3 约束) 在分类器看来等价。 |
| **信号3 动词强度** | ⚠️ 残缺 | `build_kw` 把「做/开发/搭建/帮我做」与 `chat_kw` 的「怎么/如何/为什么」并列，但**无强度分级**。结果「做个网站难吗」因含「做」被判 build（典型误判源）。 |
| **信号4 上下文连续性** | ✅ 部分 | `context.py` 有历史话题检测 + correction，但纯关键词打分，且 correction 曾把 `build/site` 错降为 `build/page`（RC2）。无「渐进铺垫 vs 突发话题」的连贯性评分。 |
| **信号5 行为信号** | ⚠️ 残缺 | 仅 `project_status` / `has_requirement_doc` / `conversation_summary` 间接可用；「是否打开代码库 / 上传设计稿 / 指定技术栈」等细粒度行为**未埋点**。 |
| **加权融合 + 三档决策** | ❌ 缺口 | 现状是固定 70/20/10 加权 + 二元路由（route / paused-plan-confirm），**无 0.7/0.4 三档（BUILD/INQUIRY/CHAT）**，也**无澄清子流程**。 |
| **LLM 结构化增强** | ⚠️ 残缺 | `semantic.py` 只回 `level1/level2/confidence/industry`，**无 `is_actionable` / `missing_specs` / `clarification_needed`**。 |

> 结论：**信号2、信号3（强度分级）、加权三档决策、澄清子流程、LLM 结构化字段** 是净新增价值；信号1/4/5 是「已有雏形但需升级」。

## 2. 你的五维信号模型（归纳整理）

把你的提案提炼为可落地的信号定义：

| 信号 | 输入 | 打分函数 | 归一化 |
|---|---|---|---|
| **S1 语义显式度** | 当前消息 | `kw_density = 命中 WEBSITE_KEYWORDS 数` | `min(kw_density/2, 1)` |
| **S2 需求完整度** | 当前消息 | `constraints = 提取(页面范围/功能点/技术栈/时间/受众)` | `min(len/3, 1)` |
| **S3 动词强度** | 当前消息 | 强(做/开发/搭建/生成/部署)=1.0；中(想要/需要/计划)=0.6；弱(了解/咨询/难吗)=0.2 | 直接取 |
| **S4 上下文连续性** | 历史 + 当前 | 渐进铺垫=1.0；无关突发=0.3；无历史=0.5 | 直接取 |
| **S5 行为信号** | 会话/项目状态 | 打开代码库/上传稿/指定栈/历史建站 = 累加上限 1.0 | `min(sum/3,1)` |

**融合（你的权重）：**

```
final = 0.25·S1 + 0.30·S2 + 0.20·S3 + 0.15·S4 + 0.10·S5
BUILD      ≥ 0.70 且 is_actionable
INQUIRY   0.40 ~ 0.70 或 clarification_needed
CHAT       < 0.40
```

**决策路由：** BUILD→Planner；INQUIRY→澄清(≤2 轮)→补充后重评/转 CHAT；CHAT→闲聊 Agent。

## 3. 候选方案对比

### A. 现状增强（最小改动）
保留 5 模块 + 70/20/10 聚合，仅在 `rules.py` 增加**动词强度分级**与**约束计数**的轻量版，把弱动词（难吗/怎么/为什么）的置信度压低，并把「0 约束」标记出来供下游参考。**不**引入加权三档、不引入澄清子流程。

### B. 纯规则五维加权（你的原始提案）
完全按 §2 实现：5 信号独立打分 → 加权融合 → 三档决策。**不调 LLM**（或仅用现有 semantic 做兜底）。

### C. 规则五维 + LLM 结构化增强（混合，推荐）
规则层算 S1–S5（快、可解释）；**复用现有 `semantic.py` 调用（~2s 已支付）**，扩展其输出 `is_actionable / missing_specs / clarification_needed / clarification_questions`；Fusion 让规则给「硬信号」、LLM 给「语义判定 + 可执行性 + 缺失规格」，二者加权出三档；新增澄清子流程（此即 **§8 三层管道** 的目标态）。

### D. 全 LLM 结构化（LLM-only）
去掉 `rules`/`context` 关键词模块，只发一轮 LLM 返回完整结构化意图（含五维自评 + `is_actionable` 等）。

### 对比矩阵

| 维度 | A 现状增强 | B 纯规则五维 | C 规则+LLM混合 ★ | D 全LLM |
|---|---|---|---|---|
| **防误判能力** | 中（缓解弱动词误判，但仍无三档） | 中（对口语/玩笑/隐喻脆弱） | **高**（硬信号+语义双保险） | 高（但黑盒不可控） |
| **延迟** | 零增量 | 零增量 | ~2s（LLM 已付，无新增） | ~2s（不可省） |
| **Token 成本** | 0 | 0 | 仅扩展现有 prompt（微增） | 最高（每轮全量） |
| **可解释/可单测** | 高 | **最高**（纯确定性） | 高（规则可单测，LLM 可日志） | 低（黑盒） |
| **与现状兼容** | **最高**（只改 rules） | 中（需新增 classifier） | 中（扩展 semantic + 新增融合） | 低（推翻重构） |
| **冷启动成本** | 低 | 高（权重需大量标校） | 中（复用现有 LLM，权重渐进标校） | 低（prompt 即文档） |
| **LLM 超时兜底** | 有（规则是安全网） | 有 | 有 | **无（致命）** |
| **行为信号利用** | 不利用 | 需埋点 | 渐进接入 | 需埋点 |
| **维护成本** | 低 | 高（词表膨胀） | 中 | 低 |

> ★ **推荐 C**：它在「防误判」与「可解释/可兜底」之间取得最佳平衡，且复用已有 LLM 调用不增延迟成本，融合逻辑可渐进标校。

## 4. 澄清策略子决策（C 方案内的关键取舍）

你的提案用「轻量澄清 ≤2 轮」处理 INQUIRY。但现状已有两条相关路径，需明确分工：

| 路径 | 适用 | 体验 | 现状 |
|---|---|---|---|
| **P1 轻量澄清（你的提案）** | 一句话里有建站意图但缺关键规格 | 反问 1–2 轮最少必要问题，不进重型流程 | ❌ 不存在 |
| **P2 需求 Agent（PRD）** | 确认要建站但需完整规格 | 路由 `agent_requirement` 生成详细 PRD + 方案卡 | ✅ 已有（v1.0.7） |
| **P3 方案确认卡** | Planner 已出方案 | `paused(await_confirm)` + 「确认并生成」 | ✅ 已有（F4） |

**建议分工：** INQUIRY 先走 **P1**（轻量澄清，≤2 轮，问最少必要项：类型/页面数/技术栈）；若 2 轮后仍缺核心规格但用户确认要建，转 **P2** 生成完整 PRD；PRD 就绪后走 **P3** 确认卡。三者形成 `澄清→需求→确认` 的递进漏斗，避免「模糊输入直接砸进重型 Planner」（你提案第⑦点已强调）。

> 澄清机制的完整细则（触发条件 / 最多 2 轮 / 显式退出 / 状态续接）见 **§9**。

## 6. 风险与未决项

1. **纯规则对口语/玩笑脆弱**：「哈哈哈做个网站哈哈」含强动词「做」+ lexical 命中，S1/S3 会拉高。需 S4 上下文或**严肃度/语气**辅助信号兜底（C 方案靠 LLM 层 `is_actionable` 补位，比 B 稳）。
2. **权重标校需标注集**：建议扩展 `scripts/run_tests.py` 回归集，新增建站意图用例（「我想做个网站」「做个网站难吗」「我们公司做外贸想做个 B 端网站」「帮我用 React 做企业官网 3 页面」等），用准确率反标权重。
3. **两套「确认」体验冲突**：P1 澄清卡 与 P3 方案确认卡 需用不同 UI 语义区分，避免用户困惑。
4. **LLM 结构化字段需 JSON Schema 校验**：`missing_specs`/`clarification_questions` 必须约束类型，防止脏数据进 Fusion。
5. **行为信号埋点越界**：代码库/上传稿检测涉及前端 + 业务侧，超出 `ai_service` 范围，P4 需跨团队排期。
6. **可观测性 token 统计缺口**：各 provider 的 token 字段名不一（需兼容 `response_metadata["token_usage"]`），统计不到记 `-1`，不影响主流程。
7. **热更新一致性**：reload 失败必须回滚到上一版 ruleset（保护在途请求）；多 Worker 场景各自 reload（或上配置中心，见 §11 策略 C）。

## 8. 整体流程架构（三层管道）

用户提出的目标架构——把扁平的「规则/语义/上下文/安全 并行 + 聚合」重构为清晰的三层线性流：

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 1  上下文重建与归一化 (Context Reconstruction & Norm.)  │
│  解析 conv_id / 拉 Chroma 项目·用户记忆 / 拼 frontend_hint     │
│  / 归一化消息(last_user, summary, checkpoint) → ContextBundle │
└───────────────────────────────────┬─────────────────────────┘
                                     ↓
┌─────────────────────────────────────────────────────────────┐
│ Layer 2  意图理解与候选生成 (LLM-based NLU)                    │
│  语义分类 + 候选意图列表 + 结构化字段                          │
│  (is_actionable / missing_specs / clarification_needed)        │
└───────────────────────────────────┬─────────────────────────┘
                                     ↓
┌─────────────────────────────────────────────────────────────┐
│ Layer 3  规则校验与决策 (Rule Engine + Policy)                │
│  五维打分 S1–S5 + 安全策略 + 融合三档 + 路由/升级/澄清         │
└───────────────────────────────────┬─────────────────────────┘
                                     ↓
                          路由到对应 Specialist
```

### 8.1 三层与现状/目标态模块对齐

| 层 | 职责 | 现状对应 | 目标态对应 |
|---|---|---|---|
| **L1 上下文重建** | 聚合 Chroma 记忆 + 选项状态 + checkpoint + summary，输出归一化 `ContextBundle` | `context.py` 的 Chroma 片段 + `pipeline` 内消息切片（散落） | 独立 `reconstruct_context()`，统一出口 |
| **L2 LLM NLU** | 语义分类 + 候选意图 + 结构化字段 | `run_semantic`（仅 `level1/2/conf/industry`） | 扩展 `semantic.py` 输出**候选列表 + 结构化字段**（P1） |
| **L3 规则校验决策** | 五维打分 + 安全 + 融合三档 + 路由/升级 | `run_rules`+`run_safety`+`_aggregate`+`run_tools` | `RuleEngine`（热加载，§11）+ `Policy`（escalate/block/clarify/route）+ `Fusion` |
| **路由** | 选 Specialist | `run_tools`→`selected_skill` | 同，新增 `clarify` 决策 → 澄清 Specialist（§9） |

### 8.2 设计要点

- **L1 / L3 是确定性、零延迟、可单测的**；**L2 是唯一耗 LLM 的层**，且调用已存在（~2s 已付，不增成本）。
- **L3 的 `Policy` 治理动作（升级/拦截/澄清）与纯打分解耦**，便于热更新（§11）——改策略不必动融合代码。
- **澄清（§9）是 L3 的一种决策输出（`decision=clarify`），不是独立层**，保持三层线性流不被破坏。
- 这是方案 C 的具象化：L2 提供语义 + 可执行性，L3 的 RuleEngine 提供 S1–S5 硬信号，二者在 L3 `Fusion` 汇出三档。

## 9. 模糊意图澄清机制（最多 2 轮）

> 对应你补充点①。与 §4 的「路由分工」互补：§4 决定「澄清卡 vs 需求卡 vs 方案卡」，本节规定澄清**机制本身**。

### 9.1 触发条件（满足任一即进入澄清）

- L2 返回 `clarification_needed = true`；
- L3 融合分落在 **INQUIRY 带（0.4–0.7）**；
- 置信度 < 阈值且非闲聊（**低置信不猜，主动反问**，呼应你提案防误判机制①）。

### 9.2 机制细则

1. **主动反问，最多 2 轮**：首轮问「最少必要」问题（类型 / 页面数 / 技术栈 / 核心功能），基于已提取信息**动态生成**（不重复用户已给项）；第 2 轮仅补仍缺失的关键规格。
2. **显式退出优先**：用户说「随便问问」「不用了」「聊天而已」→ 立即转 CHAT，停止追问（你提案防误判机制③）。
3. **模糊输入安全处理**：如「做个网站」类高模糊，先给轻量响应（"建站我可以帮你！请问是哪种类型？个人博客 / 企业官网 / 电商 / 其他？"），**不进重型 Planner**（你提案防误判机制④）。
4. **状态留存与续接**：澄清轮次计数存 Redis checkpoint（`clarify_rounds`，上限 2）；用户回复后 L1 重建上下文携带该状态，L2/L3 重评。超过 2 轮仍缺核心规格 → 降级 CHAT 或转需求 Agent（P2）生成完整 PRD，**避免死循环**（你提案防误判机制②）。
5. **与现有确认卡区分**：澄清卡（§4 P1）是「问规格」，方案确认卡（§4 P3 `paused(await_confirm)`）是「确认方案」——UI 用不同语义/文案，不混淆（风险③已记）。

## 10. 可观测性设计（每次识别必记 JSON）

> 对应你补充点②。**原则**：每次 `classify_v2` 调用必须产出一条结构化日志，供排查误判、标校权重、审计升级。

### 10.1 Schema（适配本系统字段）

```json
{
  "timestamp": "2026-07-24T19:44:00Z",
  "request_id": "req_xxx",                 // 每次 classify 生成 uuid（现状缺失，需新增）
  "conversation_id": 123,
  "user_id": "u_456",
  "raw_input": "帮我把登录功能改成支持 OAuth",
  "llm_intent": "build/modify",            // 语义层 level1/level2
  "llm_confidence": 0.87,
  "rules_triggered": ["build_kw", "verb_strong", "context_correction_blocked"],
  "decision": "route",                     // route|block|confirm|clarify|fallback|split
  "latency_ms": 1240,                      // 整条管道耗时（现状仅记 semantic.latency_ms，需补总耗时）
  "tokens_used": 3200,                     // LLM token（现状未统计，需从响应 metadata 取）
  "specialist_routed": "agent_build",      // = selected_skill
  "human_approver": null,                  // confirm/escalate 时回填
  "outcome": null                          // 后续回填: success|blocked|user_clarified|...
}
```

### 10.2 落地要点

- 新增 `intent/observability.py: log_intent_record(result, meta)`，在 `_aggregate` 返回后调用一次；`outcome` 先写 `null`，由 Worker / 前端在 specialist 完成或用户响应澄清后**异步回填**（如 `patch_intent_outcome(request_id, outcome)`）。
- `request_id` 在 `classify_v2` 入口 `uuid4()` 生成，贯穿整条链路（日志 + 回填键）。
- `tokens_used`：在 `semantic.py` 调用处从 `resp.response_metadata["token_usage"]` 提取（不同 provider 字段名不一，需兼容）；统计不到记 `-1`。
- `rules_triggered`：由 `RuleEngine`（§11）打分时累积触发的规则名列表，随 `RuleResult` 透出。
- **存储**：先落本地 JSONL 日志（零依赖），后续可接 ES/Loki；`outcome` 回填走同一 JSONL 追加或独立 outcome 流。
- **与可解释性联动**：日志即「为什么这么判」的证据链，直接服务于 §2 权重标校与 §6 误判复盘。

## 11. 规则热更新（无需重启 Agent）

> 对应你补充点③。**痛点**：现状 `rules.py` / `context.py` 的关键词、修正映射、五维权重都是**模块级常量**，改词表/权重必须重启 7102（项目约定手动重启，成本高）。**目标**：规则引擎支持动态加载，调词表/权重即时生效。

### 11.1 外置规则配置

把可变规则外置为 `intent/ruleset.json`（或 YAML），含：

```json
{
  "build_keywords": [...],  "chat_keywords": [...],  "learn_keywords": [...],
  "topic_keywords": { "网站制作": [...], ... },
  "correction_map": [ ["网站制作", {"level1":"build","level2":"site",...}], ... ],
  "verb_strength": { "strong": ["做","开发","搭建",...], "mid": [...], "weak": [...] },
  "weights": { "lexical":0.25, "completeness":0.30, "verb":0.20, "context":0.15, "behavior":0.10 },
  "thresholds": { "build":0.70, "inquiry":0.40 }
}
```

`RuleEngine` 类持 `self.ruleset`，提供 `load()`（首读）+ `reload()`（重读源）；模块级函数委托单例。L2 的 LLM system prompt 如需热更，也可外置 `semantic_prompt` 字段由 `semantic.py` 读取。

### 11.2 触发重载的三种策略对比

| 策略 | 做法 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|---|
| **A 文件 mtime 轮询** | 每次 classify 前比对 `ruleset.json` mtime，变化则 reload（可缓存 1s） | 零依赖、零接口 | 每请求一次 stat | ⭐ 起步用 |
| **B 管理端点** | `POST /admin/intent/rules/reload`（7102 内）手动触发 | 确定性、可审计 | 需鉴权（仅内网/管理员） | ⭐⭐ 配合 A |
| **C 配置中心订阅** | 监听 Redis / 配置服务变更事件 | 多实例一致、实时 | 引入外部依赖 | 规模化再上 |

### 11.3 安全约束

- reload 失败**必须回滚到上一版 ruleset**（不破坏在途请求）；
- 重载前后打印 diff 日志便于观测；
- 热更新只覆盖「规则/权重/阈值」等确定性部分；LLM 行为变更走 `semantic_prompt` 字段同机制。

> **闭环价值**：P5（日志复盘误判）→ 改 `ruleset.json` 权重/词表 → P6 热加载生效，全程**免重启 7102**，把「权重标校」（风险②）从「改码+重启」降级为「改配置+热更」。
