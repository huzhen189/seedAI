# SeedAI 架构重构方案（v2 设计稿）

> 本文档为**全新设计稿**，不纠缠现有实现细节。覆盖 6 个优化方向：
> 1. 业务配置集中化（配置项 + Redis 缓存 TTL 统一）
> 2. `Project` / `Conversation` 表合并为单一 `Conversation`
> 3. `/api/chat` 的前置校验顺序重排（鉴权 → 清洗 → 配额 → 计量 提前）
> 4. 业务端瘦身 + 前端直连分布式 AI Server（去掉 SSE 二次转发）
> 5. AI Server 重设计：清晰的生产级流程
> 6. 完整端到端流程（登录/配额 → 上下文组装 → 双索引 Chroma → SIR 约束 → JSON 组装 → 续接判定 → Worker 池 → 路由分配）

---

## 0. 设计目标与不变量

| 目标 | 说明 |
|---|---|
| 业务端极薄 | 只做"可信边界"（鉴权、配额、计量、选址、落库审计），**不碰任何 SSE 转发与 AI 编排** |
| 前端直连 AI Server | 消除"业务端 ↔ AI 核心"之间的一层 SSE 代理，延迟减半、业务端无长连接压力 |
| 上下文不塌缩 | 不靠随机 `LIMIT 5` 截断；用"近 N 条 + 项目规则 + Chroma 向量记忆"三层补全 |
| 配置即代码 | 所有"业务参数"（TTL、限额、服务发现）进 `config`，不再散落魔法数字 |
| 表结构收敛 | `Project`/`Conversation` 合并，外键深度从 3 层降到 1 层 |

**不变量（铁律）**
- 业务端是**唯一对外入口**与**可信边界**；AI Server 仅内网可达，不持有用户 Cookie。
- 所有写库的"用户消息/产物"必须经业务端落库（审计、配额、统计都在业务端），AI Server 不直接写业务 MySQL。
- AI Server 无状态、可水平扩展；每个 trace 状态只存在于 Redis（可跨 AI Server 实例续接）。

## 1. 配置集中化（已完成落地，此处记录设计）

新增 `backend/business/app/config.py::Settings` 业务配置项（已从魔法数字迁移）：

```python
# 对话/上下文相关配置（集中管理）
chat_recent_redis_ttl:    int = 1800     # 最近对话上下文 Redis 滑动窗口 = 30min（原硬编码 600s）
chat_recent_limit:        int = 10       # 组装给 AI 的"最近 N 条消息"上限（原 LIMIT 5）
conversation_summary_ttl: int = 1800     # 对话摘要滑动窗口 = 30min（原硬编码 86400）
ai_servers:               str = ""       # 分布式 AI 服务发现列表（逗号分隔 base URL），空则回退 ai_service_url
ai_server_health_path:    str = "/healthz"
```

**配置读取约定**
- 所有与环境/部署相关的参数通过 `.env` + pydantic `BaseSettings` 注入；代码内**禁止**写裸 `600`/`86400`/`5` 这类魔法数字。
- AI Server 侧同步新增一份等价 `config`（模型路由、Chroma 地址、worker 池大小、超时），同样集中。
- 后续新增业务阈值（意图阈值、截断长度、重试次数）一律走配置，不在函数内硬编码。

**本次改动落点（已 commit 前的 diff）**
- `config.py`：新增上表 5 个字段。
- `proxy.py::_build_messages_from_db`：3 处 `ex=600` → `settings.chat_recent_redis_ttl`；`limit(5)` → `settings.chat_recent_limit`。
- `proxy.py::get_summary/save_summary/maybe_compress_summary`：`setex(..., 86400, ...)` → `settings.conversation_summary_ttl`。

## 2. 数据模型：Project + Conversation 合并

### 2.1 现状问题
- `projects` 与 `conversations` 存在**大量重叠语义**：项目其实就是"一组会话 + 一份共享 system_prompt + 一份 requirement_doc + 一个建站状态"。
- 外键链 `Message → Conversation → Project → User` 三层，查询任何上下文都要跨 3 张表 `JOIN`，且"软删除/分享/预览"逻辑分散在两张表。
- 前端左栏"项目"与"会话"两级，但实际用户心智是"一个对话就能生成一个站"，两级结构是过度设计。

### 2.2 合并方案：单一 `Conversation`

把 `Project` 的字段**下沉**进 `Conversation`，去掉 `Project` 表。

```python
class Conversation(Base):
    __tablename__ = "conversations"

    id: int            # PK
    user_id: int       # 归属用户（直接绑定，不再经 project 中转）
    # —— 原 Project 下沉字段 ——
    title: str                      # 会话标题（同时作为"站点名"候选）
    share_id: str | None            # 公开分享令牌（UUID）
    is_public: bool = False         # 是否公开
    preview_url: str | None         # 最新 COS 预览直链
    system_prompt: str | None       # 项目级系统提示（动态积累）
    build_status: str = "draft"     # 建站状态: draft→planning→planned→building→built
    requirement_doc: str | None     # 需求文档 JSON（requirement_agent 产出）
    deleted_at: datetime | None     # 软删除（保留关联数据）
    # —— 原 Conversation 字段 ——
    status: str = "active"          # 会话状态: active|paused|completed|aborted|error
    checkpoint_stage: str | None    # 断点续跑阶段
    checkpoint_data: str | None     # 断点 JSON 快照
    progress_pct: int = 0
    created_at / updated_at

class Message(Base):
    __tablename__ = "messages"
    id / conversation_id / role / content / model_id / trace_id / created_at
    # 新增：parent_msg_id（可选，支持分支/编辑重写）
```

### 2.3 迁移与兼容
- 旧 `projects` 行按 `id` 映射：每个 `project` → 一条 `conversation`（保留其 `system_prompt`/`requirement_doc`/`status`），原 `conversations` 行**直接改 `user_id` 为 project 的 user_id** 并保留。
- `reset_all.py`、后台统计、分享逻辑统一改为只认 `conversations`。
- 提供一次性迁移脚本 `scripts/migrate_project_to_conversation.py`（双写校验 + 回滚开关）。
- **外键深度降为 2 层**：`Message → Conversation → User`，查询上下文少一次 JOIN。

## 3. `/api/chat` 前置校验顺序重排

### 3.1 现状问题（你指出的核心）
原 `proxy.py` 把"组装 messages / 调 AI / 回写"混在一起，校验散落、且**在鉴权/配额之前就做了大量 DB 查询**，浪费连接与 SQL。

### 3.2 新顺序（前置拦截，失败即返回，不做任何 DB 重活）

```
┌─ [0] 解析 & 基础校验（无 DB）
│    - 解析 query/body（model / conversation_id / q / cursor / confirmed / clarified ...）
│    - q 非空校验、长度上限、XSS/注入粗洗（只做"安全清洗"，不做语义清洗）
│
├─ [1] 鉴权（Auth，1 次 Redis/DB 读 token 解析）
│    - 校验 JWT / Cookie；无有效身份 → 401 立即返回（不碰 MySQL）
│    - 解析出 user_id、plan 等级
│
├─ [2] 配额 & 计量（Metering，纯 Redis 计数，无业务表写）
│    - 按 user_id + plan 查 Redis 日配额（INCR + EXPIRE）
│    - 超额 → 429 立即返回（不碰 MySQL、不调 AI）
│
├─ [3] 会话归属校验（轻量，1 次主键查）
│    - conversation_id 存在且 user_id 匹配？（防越权）
│    - 不存在则**仅在此刻**创建 Conversation 行（1 次 INSERT）
│
├─ [4] 选址（Service Discovery，纯内存/Redis）
│    - 从 ai_servers 健康列表中选一个 AI Server（负载/就近）
│    - 返回该 base URL（前端直连用）
│
└─ [5] 返回"直连票据"
     - 业务端**不再 SSE 转发**，而是返回：
       { ai_server_url, conversation_id, token(短期直连令牌), stream_hint }
```

**关键变化**
- 鉴权/配额/计量**全部在 MySQL 重查询之前**；任何拦截分支都不触发 `select Message`、不触发 AI 调用。
- "取最近消息组装上下文"等重活，从业务端**移除**——改由 AI Server 侧负责（见 §5），业务端只负责"把 conversation_id + 直连令牌给前端"。
- 业务端在这一步只做 **1 次 token 解析 + 1 次 Redis 配额 + 1 次 conversation 主键校验/插入**，远轻于现状。

## 4. 业务端瘦身 + 前端直连分布式 AI Server

### 4.1 现状损耗
> 前端 → 业务端（SSE 接收、再逐帧转发）→ AI 核心（生成）→ 反向透传。
> 业务端持有一条**长连接 + 转发循环**，既占连接又引入一层缓冲延迟，且 AI 核心无法水平扩展（前端只认单业务端，业务端又只认单 AI 核心）。

### 4.2 新架构（前后端分离直连）

```
┌─────────┐    ① GET /api/chat/entry        ┌──────────────┐
│ 前端    │ ───────────────────────────────► │ 业务端(薄)   │
│(7100)   │ ◄──── ② {ai_server_url,token} ── │ (7101)       │
└─────────┘                                  │ 鉴权/配额/选址│
     │ ③ EventSource(ai_server_url/stream)    └──────────────┘
     │                                         （不持有 SSE 长连接）
     ▼
┌──────────────────────────────┐
│ AI Server 集群(多个, 内网)    │
│  /stream 直出 SSE             │
│  - 上下文组装(读自己 Redis)   │
│  - 意图路由 / Worker 池        │
│  - 写回经业务端 API 落库       │
└──────────────────────────────┘
```

### 4.3 业务端在新架构中的职责（极薄）
1. **可信边界**：JWT/Cookie 鉴权、配额、计量（`§3` 已重排）。
2. **服务发现**：返回健康 AI Server 地址 + 短期直连令牌（`ai_connect_token`，5 分钟有效，绑定 user_id+conversation_id）。
3. **落库审计代理**：AI Server 不直接写业务 MySQL；它通过一个**受信内部 API** `POST /api/internal/append-message`（带 `ai_connect_token` 校验）把 user/assistant 消息、产物版本、trace 状态回写业务端数据库。
4. **统计/分享/预览**：仍由业务端提供（这些是"资产"层，不属于 AI 推理）。
5. **断连取消协调**：前端断开时，业务端记录 `clients:{tid}`，并通过内部 API 通知 AI Server 取消 Worker（或 AI Server 自己靠 SSE 写失败感知断连）。

### 4.4 前端改动
- 原 `startChat` 改为两步：先 `GET /api/chat/entry` 拿 `ai_server_url`，再 `new EventSource(ai_server_url + '/stream?token=...&conversation_id=...&q=...')`。
- 重连/回放：同一 `trace_id` 复用，AI Server 自身 `stream_exists(tid)` 回放，业务端不介入。
- 直连令牌防盗：短时效 + 绑定 conversation，AI Server 侧校验失败直接 401。

## 5. AI Server 重设计：清晰的生产级流程

> 此节为**全新实现规格**（你说"先不要管现在的代码"）。AI Server 不再做"业务编排"，只做"推理编排"，且**所有上下文/记忆/历史都在 AI Server 侧闭环**（从自己的 Redis/Chroma 读，不依赖业务端传 messages）。

### 5.1 入口 `/stream`

```
请求: GET /stream?token=&conversation_id=&q=&model=&cursor_id=&confirmed=&clarified=&trace_id=
```

**阶段 A — 接入校验（接入层，无重活）**
1. 校验 `ai_connect_token`（业务端签发，绑定 user+conv），失败 401。
2. 解析参数：`q`（当前输入）、`model`、`confirmed/clarified`（流程控制标志）、`trace_id`（续接或新建）。
3. 校验 conversation 存在（轻量，必要时回查业务端内部 API）。

**阶段 B — 上下文组装（Context Assembly）**
> 这是取代"随机 LIMIT 5 + Redis 缓存污染"的核心层。组装一个结构化 `ContextBundle`：

```
ContextBundle = {
  recent_messages:  Message[]      # 最近 N 条（业务端 API 拉取，分页由 cursor 控制，不再硬 LIMIT）
  project_rule:     str            # 项目级 system_prompt + requirement_doc 摘要
  conv_memory:      VectorHit[]    # Chroma: conv 索引（本会话历史向量记忆，逐条 upsert）
  project_memory:   VectorHit[]    # Chroma: project 索引（跨会话项目知识，逐条 upsert）
  sir_constraints:  Constraint[]   # SIR 约束（删除信号/建站强相关关键词/安全红线/格式要求）
  slots:            SlotState      # 跨轮槽位记忆（intent:slots:{conv_id}，粘性信念）
}
```

- **近 N 条消息**：调业务端内部 API `GET /api/internal/messages?conv=&cursor=&limit=` 分页拉取，**默认取最近 `chat_recent_limit` 条**，绝不无脑截断最早意图。
- **Chroma 双索引**：
  - `conv` 集合：本会话每条消息 embedding 后 **upsert**（向量 = 句向量；metadata = role/content/time）。检索时取 top-K 相似历史，补全"近 N 条"看不到的早期语义。
  - `project` 集合：项目级知识（需求文档切片、历史选型决策、用户偏好）独立索引，跨会话持久。
  - 每次对话结束，**逐条 upsert** 新消息到两个集合（conv 必写，project 仅当命中"项目知识"规则时写）。
- **SIR 约束**：从规则库加载（删除信号关键词、建站强意图词、安全策略），作为**硬约束**注入后续判断（见 §5.2）。

**阶段 C — 组装决策 JSON（DecisionRequest）**
把 `ContextBundle + q + flags` 包成一个 JSON 对象，作为 Worker 的唯一输入：

```json
{
  "trace_id": "t_xxx",
  "conversation_id": 123,
  "user_id": 42,
  "q": "品牌旗舰店型",
  "model": "qwen",
  "flags": { "confirmed": false, "clarified": false },
  "context": { "recent": [...], "project_rule": "...", "conv_mem": [...], "project_mem": [...] },
  "constraints": { "delete_signals": [...], "build_keywords": [...], "safety": [...] },
  "slots": { "prior_intent": "build/doc", "collected": {...} }
}
```

**阶段 D — 续接判定（stream_exists）**
```
if stream_exists(trace_id):
    → 回放模式：从 Redis 读已缓存的事件流，重发给前端（断线重连/刷新不新建 Worker）
else:
    → 新建：enqueue(worker_pool, DecisionRequest)，返回 trace_id 让前端后续可续接
```
- `trace_id` 由前端在重连/续跑时复用；首次请求由 AI Server 生成并返回。

**阶段 E — Worker 池执行**
进 Worker 后**不再做"历史重查"**，直接用 `DecisionRequest.context`：

```
[1] 输入规整：q 清洗 + 槽位合并（slots.collected + 本次 q）
[2] 选项选择短路 resolve_selection：
      若 q 命中"删除信号/建站强关键词/历史待选项回复" → 直接 route（不经过 LLM）
      （修复原"品牌旗舰店型"被当闲聊的问题：选型回复应走此短路）
[3] 简单/单意图 → 轻量路由（规则 + 向量 top-K 已够）→ 直接出 plan
[4] 复杂 / 多意图 / 低置信 → 统一走 LLM 语义判断：
      - LLM 仅对 DecisionRequest（已含上下文+约束）做终判
      - 产出 decision + subtasks[] + missing_slots + clarify_options（如需追问）
[5] 执行计划：subtasks[] 交给 router 分配执行
      router 按 skill 类型（chat/build/doc/qc）派发到对应 executor
      多 subtask 可并行/串行，带依赖图
[6] 槽位回填：执行中补全的 slots 写回 intent:slots:{conv_id}（粘性信念）
[7] 终态：发布 done / aborted / clarify(暂停等用户) / unsupported
```

**阶段 F — 落库回写（经业务端内部 API）**
- Worker 每产生一条 user/assistant 消息或产物版本，调 `POST /api/internal/append-message`（带 token）。
- AI Server **不直接连业务 MySQL**，保证业务端对"资产/审计"的唯一 ownership。

### 5.2 SIR 约束的位置（修复"跨轮记忆被短路"）

> 原混合级联的致命 bug 是"新奇度兜底在 load_slots 之前 return"。新设计从结构上杜绝：

- `slots`（跨轮意图/槽位）在**阶段 B 就装入 `ContextBundle`**，永远在 `resolve_selection` 和 `LLM 终判` 之前可用。
- `resolve_selection` 和 `LLM` 判断时，**先读 `slots.prior_intent`**：若 prior 属于 `build/doc` 且会话处于"建站流程中"，则**禁止**判为 `chat_casual` 闲聊——这是 SIR "粘性信念"的等价实现，且不被任何早退绕过。
- "删除信号/建站强关键词"等约束在阶段 E[2] 的 `resolve_selection` 短路**最高优先**，先于所有模糊判定。

### 5.3 clarify 暂停/续跑（沿用已设计的 clarified 链路，且修复透传）

- `[4]` 若 LLM 判 `clarify`：发布结构化 `clarify` 事件（`options/multi/free_text_hint`）后 **`done` 并暂停**，把 `DecisionRequest` 快照存 `pending_clarify:{conv_id}`。
- 前端选填后带 `clarified=true` 重发：阶段 D `enqueue` 时 Worker 读 `pending_clarify`，**跳过 [3]/[4] 重分类**，直接用快照意图 + 注入答案 → `[5]` 执行。
- **修复点**：`clarified` 必须作为 `DecisionRequest.flags.clarified` 显式透传（原实现 GenerateReq 漏字段导致空转，已在 `docs/06` 记 R1）。

## 6. 完整端到端时序（一次性看清）

```
用户: "品牌旗舰店型"（此前说过"生成产品需求文档"）
│
├─[前端] GET /api/chat/entry {q, conversation_id}
│   └─[业务端 薄]
│       [0] 解析+粗洗 q
│       [1] 鉴权(JWT)            ← 失败 401 立即返回
│       [2] 配额(Redis INCR)     ← 超额 429 立即返回
│       [3] conversation 存在?   ← 轻量主键查/建
│       [4] 选址: 选 ai_server_2 (健康)
│       [5] 返回 { ai_server_url, ai_connect_token(5min), trace_id }
│
├─[前端] EventSource(ai_server_2/stream?token&conv&q&trace_id)
│   └─[AI Server]
│       A 接入校验(token)        ← 失败 401
│       B 上下文组装:
│           - 拉最近 10 条消息(业务端内部 API, 分页不再硬截断)
│           - project_rule(需求文档摘要)
│           - Chroma conv/project 双索引 top-K
│           - SIR 约束(删除信号/建站词)
│           - slots.prior_intent=build/doc  ← 跨轮记忆在此已就位
│       C 组装 DecisionRequest JSON
│       D stream_exists? 否 → enqueue Worker
│       E Worker:
│           [1] 规整+槽位合并
│           [2] resolve_selection: "品牌旗舰店型" 命中历史选型回复 → 直接 route(build/doc)
│               （即使向量 0 命中，也不再误判闲聊）
│           [5] router 派发 → doc executor 生成产品需求文档
│           [6] 槽位/产物回写 intent:slots + 业务端内部 API
│           [7] 发布 token/plan/chunk/done
│       F 业务端内部 API 落库(user/assistant/artifact)
│
└─[前端] 渲染 PRD 文档 / 预览
```
