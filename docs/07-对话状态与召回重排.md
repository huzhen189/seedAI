## 一、SIR 对话状态

### 1.1 数据结构（核心真相源）

定义在 `core/contracts.py:187`：`SirState`（Pydantic，`extra="forbid"`）。

```python
class SirState(ContractModel):
    slots:        dict[str, Any]            # 槽位：单值(str) + 多值(list)
    constraints:  list[dict[str, Any]]      # 约束，按 kind 去重
    pending:      list[dict[str, Any]]      # 待办动作（追加后截断到 20）
    memory_hints: list[dict[str, Any]]      # 记忆提示（追加后截断到 20）

class SirDelta(SirState): pass              # delta = 同形状，表示「本轮增量」
```

**关键**：槽位值是**裸值**，不是旧版 `{value,confidence,status,source}` 包裹。例：`"site.theme": "light"`、`"site.sections": ["hero","about"]`。

### 1.2 DST 之前（sir_base）长啥样

由 **S1** 从 `sir_snapshots` 表取「最新 base 快照」加载；若为回溯控制（correct/supplement），则取 **prior_turn 快照**（=回滚到上一轮结束态）。

```json
{
  "slots": {
    "site.theme": "light",
    "site.type": "portfolio",
    "site.sections": ["hero", "about", "contact"],
    "site.style": ["简约", "科技"],
    "site.brief": "个人作品集"
  },
  "constraints": [{"kind": "theme", "value": "浅色为主"}],
  "pending": [{"action": "补充联系方式"}],
  "memory_hints": [{"hint": "用户偏好浅色"}]
}
```

本轮用户说「改成深色，再加个博客板块」→ **S2** 用确定性 `_extract_slots`（`router/intent.py:186`，**零 LLM 成本**）抽出 delta：

```json
{                                          // SirDelta
  "slots": {
    "site.theme": "dark",                  // 单值→要覆盖
    "site.sections": ["blog"]              // 多值→要并集
  },
  "constraints": [], "pending": [], "memory_hints": []
}
```

### 1.3 DST 之后（sir_after_dst）长啥样

**S3**（`core/stages/s3_dst.py`）按槽位语义分流合并：

```json
{
  "slots": {
    "site.theme": "dark",                               // ✅ 覆盖（改主意以最新为准）
    "site.type": "portfolio",                           // 未动，保留
    "site.sections": ["hero","about","contact","blog"], // ✅ 并集累积（只增不抹）
    "site.style": ["简约","科技"],
    "site.brief": "个人作品集"
  },
  "constraints": [{"kind": "theme", "value": "浅色为主"}],
  "pending": [{"action": "补充联系方式"}],
  "memory_hints": [{"hint": "用户偏好浅色"}]
}
```

### 1.4 合并规则（按语义分流，非一律 dict 覆盖）

| 槽位类型 | 例子 | 合并策略 |
|---|---|---|
| 单值槽位 | `site.theme` `site.type` `site.brief` | **后写覆盖**（改主意以最新为准） |
| 多值槽位 | `site.sections` `site.style` | **并集累积**（「再加一个」只增不抹）；显式 `[]` 或 `_CLEAR` 哨兵 = 清空 |
| constraints | `{kind:"theme",...}` | 按 `kind` 去重覆盖，截断 20 |
| pending / memory_hints | — | 追加，截断最近 20 条，防无界增长 |

多值槽位防御上限 `_UNION_SLOT_CAP=24`（超出保留最近 24，最旧过期遗忘）。

### 1.5 sir_diff（可回放/审计）

S3 同时产出 diff，落到 `sir_snapshots` 形成 `prev_snapshot_id` 链 + SSE `state_diff` 事件 + 一条 INFO 日志：

```json
{
  "added": [],
  "updated": [
    {"key": "site.theme",    "from": "light", "to": "dark"},
    {"key": "site.sections", "from": ["hero","about","contact"], "to": ["hero","about","contact","blog"]}
  ],
  "removed": [], "unchanged_count": 3,
  "base_snapshot_id": 123, "result_snapshot_id": 124
}
```

### 1.6 生命周期

```
S1 加载 sir_base ──► S2 抽 sir_delta ──► S3 合并 ──► sir_after_dst
(从 sir_snapshots)    (确定性, 0 LLM)        (语义分流)     │ 唯一真相
                                          ┌────────────┴───────────┐
                                       S6 建站 / S7 固化 / 下一轮 S1 基态
```

`sir_after_dst` 是 S6 建站、S7 固化、及**下一轮 S1 基态**的唯一真相源；纯闲聊轮不刷快照。

## 二、召回重排（rerank）

### 2.1 结论

项目**有 rerank，但不是 cross-encoder / LLM 语义重排器**。它做的是：**向量召回后，用用户的「软偏好」标签对召回段做带权关键词重排**，且软偏好本身**不进 prompt**（只当排序信号）。

### 2.2 实现位置与流程

在 `S1RecallStage._load_memory_recall`（`core/stages/s1_recall.py:169`）的 L5 向量召回路：

```
1. Chroma 向量召回 memory 集合（top_k = settings.memory_recall_top_k）
2. 命中经 (source_type, source_id) 回 MySQL 取标题/正文
   - message       → 取 summary 进 project_context
   - project_event → 跳过正文注入（事件不进 prompt）
   （软偏好此路不出现：软偏好从不写向量库，不参与向量召回回查）
3. 拉该 user 的软偏好（**直接读 MySQL `user_soft_preferences` 表**，非向量召回）
4. 对每个召回段算分 → 按分降序排序 → 有序注入 project_context
```

### 2.3 重排打分逻辑（核心，s1_recall.py:228 起）

```python
# 预提取每条软偏好的关键词集合（tag+content 拆词 + 中文长片段滑窗）
pref_kw = [(int(p.weight), _pref_keywords(p)) for p in soft_prefs]

def _score(text: str) -> int:
    s = 0
    for weight, kws in pref_kw:
        # 每条软偏好只计一次权重：命中任一词即 +weight（不再整串前缀限制）
        if any(k in text for k in kws):
            s += weight
    return s

backfilled.sort(key=lambda x: _score(x[0]), reverse=True)   # 按分降序
```

`_pref_keywords(p)` 的提取策略（低成本、纯子串、非语义）：
- **拆词**：把 `tag` 与 `content` 按标点/空白切分，每段 ≥2 字即为候选关键词；
- **中文滑窗**：对 ≥6 字且无空格的中文片段，补 2/3/4 字 n-gram（如「喜欢极简留白」→ `极简`/`留白`/`极简留`/`简留白`…），解决「长而无标点短语永远匹配不到」的盲区；
- **去重**：全局 `seen` 去重，`_pref_keywords` 只返回 ≥2 字关键词。

本质：仍是**带权重关键词重叠启发式、零语义**，但已不再依赖「content 前 12 字整串」这种苛刻条件——抽象 `tag`（如「设计风格」）搭配带描述性 `content`（如「喜欢极简留白」）也能通过滑窗命中召回段里的「极简」「留白」。

### 2.4 软偏好从哪来、长啥样

- **写入**：`memory_write.py` 从 LLM 抽取 → MySQL `user_soft_preferences`（字段 `user_id / tag / content / weight`，默认 `weight=50`，按 `(user_id, tag)` 幂等 UPSERT）。**软偏好不写向量库**——rerank 时由 s1 直接读 MySQL，不依赖向量召回。
- **定位**（`db/repositories/user_soft_preferences.py:17`）：同一 `(user_id, tag)` 只更新 `content/weight`，不重复插。

### 2.5 例子（⚠️ 匹配是逐字子串，非语义）

打分逻辑（`s1_recall.py:228`）：对每段召回文本 `text`，依次看每条软偏好——**`tag` 整串是 `text` 子串 → +weight；否则取 `content` 前 12 字符，整串是 `text` 子串 → +weight**（都满足才算）。是关键词重叠启发式，**不含任何语义理解**。

软偏好表（新逻辑下 `tag` 写抽象名也行，靠 `content`+滑窗兜底命中）：

| tag | content | weight |
|---|---|---|
| 极简 | 用户偏好极简留白 | 80 |
| Vue | 偏好用 Vue 搭组件 | 50 |

向量召回 3 段正文：
1. `"首页采用大量留白与极简排版"` → `极简`/`留白`(滑窗)命中 → **80** ✅
2. `"用 Vue 搭建组件化页面"` → `Vue` 命中 → **50** ✅
3. `"普通营销文案一段"` → 无关键词命中 → **0**

重排后顺序 `1 → 2 → 3`。

多偏好累加：若同时命中「极简」(80) 与「Vue」(50)，该段得 **130**。

反例对比旧逻辑（已修复）：旧版 `tag="设计风格"` + `content="喜欢极简留白"` 对 `"大量留白+极简栅格"` 永远 0 分（无连续"设计风格"、无连续"喜欢极简留白"）；新版经 `content` 滑窗拆出 `极简`/`留白` n-gram 命中 → **80**。这就是本次低成本改造消除的盲区。

### 2.6 要点

- **L2 强事实 ≠ 软偏好**：`user_facts`/`project_facts` 零容错强事实直接进 `user_context` 压 L5；软偏好**只 rerank、不进 prompt**，互不干扰。
- **旧 `user_preferences` 召回**（`_load_user_preferences`，s1_recall.py:249）是兼容保留路径，**无 rerank**，召回即按原序 append。
- **fail-soft**：拉软偏好失败 → `soft_prefs=[]`，退化为向量召回原始顺序，不影响主链路。

### 2.7 语义级 rerank 落地方案（待拍板，未实现）

现有 `keyword` 方案是**字面匹配、零语义**（「留白」与「呼吸感」命中不了彼此）。要识别同义词/上下位，需 cross-encoder reranker（交叉编码 `(query, passage)→ 相关性分数`，**非生成式模型，不能替代 qwen 聊天**）。

#### 现状地基（决定落地成本）
- 项目**无本地推理运行时**：`requirements.txt` 零 torch/transformers/onnxruntime；LLM 全云端 API（`qwen`/`deepseek`，`AsyncOpenAI`），embedding 云端 `text-embedding-v3`。
- 候选规模小：`memory_recall_top_k` 默认 5、上限 20（`settings.py:335`）——rerank 每轮只打 5~20 对，**算力/金钱成本极低（自托管≈0）**，真成本在**新增依赖 + 模型常驻内存**，不在账单。

#### 选型与架构
- **模型**：`BAAI/bge-reranker-v2-m3`（中英多语、Base 量级、中文首选）。
- **运行时**：`app/ml/inference.py` 进程内**懒加载单例**（首次调用加载权重到进程内存，之后全程复用）；接口 `app/ml/rerank.py::rerank(query, passages) -> list[float]`。
- **可复用**（用户诉求"其他调用复用"的真实落点）：
  1. *复用同一本地推理运行时*——ONNX/torch 引擎一次部署，未来挂本地 embedding / 本地小 LLM（qwen2.5-0.5B）共用，不必每个模型装一套；
  2. *复用重排能力模块*——S1 记忆召回、research RAG、web/工具结果排序全走同一 `rerank()`，不各自造轮子。
- **接入点**：`s1_recall.py` 排序步，叠加/替换于 keyword 分之上，配置 `rerank_mode: keyword | model | hybrid`。
- **fail-soft**：模型加载失败或推理超时 → 自动回退 keyword 方案，主链路零风险。

#### 方案对比表（决策用）

| 维度 | A. 仅 keyword（现状） | B. ONNX 单例 reranker（推荐） | C. torch 完整 + 本地小 LLM |
|---|---|---|---|
| 本地依赖体积 | 0 | 几十 MB（onnxruntime） | 上 GB（torch/cuda） |
| 模型权重常驻内存 | — | ~300–600 MB（bge-m3） | + 小 LLM 数 GB |
| 延迟（top_k≤20, CPU） | 0 | <50 ms 批处理 | 略高，GPU 更快 |
| 语义理解（同义/上下位） | ✗ 无 | ✓ 有 | ✓ 有 |
| 复用运行时给 embedding/LLM | ✗ | ✓ ONNX 可挂 | ✓ 最强 |
| 部署复杂度 | 无 | 进程内单例，最简单 | 重，需管 GPU/显存 |
| 金钱边际成本 | 0 | 0（自托管） | 0（自托管） |
| 首次加载耗时 | — | 秒级 | 秒~十秒级 |

#### 形态对比（部署）
- **进程内单例（推荐）**：FastAPI 进程内懒加载，首次加载后全程复用，实现最简单，满足"复用运行时 + 重排模块"诉求，契合当前单进程架构。
- 独立本地推理服务（HTTP/gRPC）：多实例共享模型、资源隔离好，但运维复杂，当前单进程架构没必要。

#### ⚠️ 硬件适配（生产=轻量服务器 2 核 / 4GB / 80GB 系统盘）
- **内存是硬约束**：4GB 要同时跑 后端(uvicorn + Chroma + 业务) + MySQL + Redis，余量通常只剩 **1~1.5GB**（实测开发机单个 uvicorn 进程即占 0.7~0.67GB）。`bge-reranker-v2-m3` 常驻 **~0.6–1.2GB**（torch 版更重、ONNX 版较轻但也要几百 MB），**加上即逼近 OOM 红线**，2 核 CPU 首次加载还会卡数秒~十秒、推理时抢 1~2 核。
- **磁盘**：80GB 若已分系统+数据，模型权重(~400MB–1GB)+ 依赖(onnxruntime 几十 MB / torch 上 GB)需确认剩余空间，torch 方案大概率塞不下或挤压业务数据。**强烈建议 ONNX 方案（几十 MB 引擎）**。
- **结论**：该轻量服务器**能跑 ONNX 版 bge-reranker，但属"贴线运行"**——必须（1）`rerank_mode` 默认 `keyword`，模型 rerank 显式开启；（2）**首次加载放后台 + 严格 fail-soft**，加载失败/超时立即回退 keyword，绝不因模型拖垮主链路；（3）监控 RSS，预留被 OOM kill 的兜底。若内存始终吃紧，**保持 keyword 方案（0 依赖）是最稳选择**。
- 候选规模 `top_k≤20` 使推理本身 CPU 开销极小（<50ms 批处理），瓶颈只在**常驻内存与加载耗时**，不在每轮算力。

> 结论：语义级 rerank 在 top_k≤20 下**不算贵**，但**在 4GB 轻量服务器上是"贴线"部署**——推荐 **B(ONNX) + 进程内单例 + 默认 keyword 回退**，fail-soft 兜底；torch/本地小 LLM（C 档）在 4GB 机器上不建议。是否启用模型 rerank 由配置开关控制，保持可降级。

## 三、一句话总结

- **SIR** = `slots/constraints/pending/memory_hints` 四元组，槽位裸值（非包裹）；DST 前是 S1 从快照链加载的基态，之后是 S3 按「单值覆盖 / 多值并集 / 约束去重 / 待办追加截断」合并出的新态，并附 added/updated/removed 的 diff 供回放与审计。
- **rerank** = 向量召回后用用户软偏好标签做带权关键词重排（非语义重排器），软偏好不进 prompt，fail-soft。语义级 rerank（cross-encoder，本地小模型进程内单例方案）见 §2.7，待拍板落地。
